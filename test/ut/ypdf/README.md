# ypdf unit tests

Tests that lock down `ypdf`'s text-positioning behavior against a
ground-truth reference renderer. PDF text layout is fragile — the
producer assembles spans by walking a text matrix that gets mutated by
every glyph's advance, every `Tc`/`Tw`/`Tz`/`TL` state change, every
`Td`/`TD`/`Tm`/`T*` move, and every `[…]TJ` kern. A one-pixel drift in
any of those compounds across a line and looks, on screen, like
"first word OK, rest off". Hard to spot without a reference; trivial to
miss in eyeball testing.

## Why mutool

[mutool](https://mupdf.com/) is the CLI front-end for **MuPDF** — a
production PDF renderer (Adobe-clean reimplementation, used by hundreds
of products). For every PDF we can ask `mutool` for:

- per-character `(x, y, font, size, glyph)` placements (`-F stext`),
- raster output for visual sanity checks (`-F png`).

These are facts about the PDF, not derivative code. Comparing our
output to mutool's is the cheapest way to know whether a regression is
"ypdf bug" or "rendering nuance". MuPDF is AGPL — we don't link against
it; we run the CLI as a build/test-time tool only.

## What's tested

| Test                  | PDF                          | Asserts                                                                                          |
|-----------------------|------------------------------|--------------------------------------------------------------------------------------------------|
| `ypdf_render`         | `test-comprehensive.pdf`     | Smoke: render returns OK, emits some spans.                                                      |
| `ypdf_positions`      | `pdf-sample.pdf`             | Per-line endpoints AND per-character cursor positions match mutool stext within tight tolerances. |
| `ypdf_font`           | bundled DejaVu TTF           | `raster_font` measure round-trips, advances are non-zero, etc.                                   |

`ypdf-positions-test` is the main coverage. It runs in three layers, in
increasing strictness:

1. **Shape sanity** — total span count, x/y/font_size ranges, no spans
   at identical `(x, y)` (catches the "text matrix never advances"
   regression where every Tj lands at the same coordinate).
2. **Per-line endpoints** — leftmost-x and rightmost-x for each
   baseline match `pdf-sample-expected-lines.h`. Catches whole-line
   shifts and cumulative drift.
3. **Per-character cursor** — for every TEXT_SPAN, walk char-by-char
   accumulating the patched-TTF advance + Tc/Tw spacing the producer
   baked into the prim, then verify each computed `(x, y, c)` lands
   within ±3 px of *some* mutool-reported char with the same codepoint
   on the same baseline. ≥98% match required (currently 100% on
   `pdf-sample.pdf`).

## How the ground truth gets generated

`pdf-sample-expected-lines.h` and `pdf-sample-expected-chars.h` are
**generated**, not hand-written. They come from running mutool against
the sample PDF and post-processing the stext XML into header-form C
arrays. A regen script lives next to the PDFs (or you can produce
equivalents with the python snippet in the test source comments). When
the sample PDF changes, regenerate both headers; do not hand-edit.

### Quick regen recipe

```sh
mutool draw -F stext -o /tmp/stext.xml test/ut/ypdf/pdf-sample.pdf
# Then:
#   python3 tools/stext-to-expected-lines.py /tmp/stext.xml > test/ut/ypdf/pdf-sample-expected-lines.h
#   python3 tools/stext-to-expected-chars.py /tmp/stext.xml > test/ut/ypdf/pdf-sample-expected-chars.h
```

(The python helpers parse `<char quad="…" x="…" y="…" c="…"/>` and emit
the C arrays. Match-tolerance constants live in the test, not in the
generated headers, so headers stay regen-stable.)

## What the test simulation does NOT cover

The per-character sim uses `raster_font::measure_text` against the
in-memory TTF (the same bytes the producer hands to ydraw). The
canvas, at runtime, walks glyphs via `gm[4]` from the per-instance MSDF
font's metadata buffer (populated from a `.cdb` generated by either
`ymsdf-gen` (CPU) or `ymsdf-wgsl` (GPU) from those same TTF bytes).
Both paths read the same FreeType-parsed hmtx, so they should produce
the same advance — but a regression in the CDB generator (or the
binder/dispatcher routing glyphs to the wrong slot) can cause a visible
gap that the sim misses.

The diagnostic block at the bottom of `ypdf-positions-test.c` prints
the per-char cursor for any span containing `"sma"` (the canonical
"smaller" smoke). When a real-world rendering bug surfaces, run the
test, then inspect:

- The diagnostic dump (test stderr) — what the sim *expects*.
- `tools/cdb-viewer ~/.cache/yetty/ydraw-fonts/pdf_<hash>.cdb` — what
  the canvas *actually* uses for advances/bearings.
- A side-by-side `mutool draw -F png` of the PDF — what it should
  *look* like.

If sim ≠ CDB, the bug is in the CDB generator (or the patcher writing
the wrong hmtx the generator reads). If sim == CDB but render is wrong,
the bug is downstream of the CDB — binder, dispatcher, shader, or atlas
packing.

## Why we don't link MuPDF

License (AGPL) + dependency weight. We use the `mutool` CLI as a
test-time *external reference*; nothing in the runtime depends on it.
The ground-truth headers are facts about specific PDFs (positions in
device space), not derivative code. If MuPDF disappeared tomorrow the
headers would still be valid against the bundled PDFs.

Any other production PDF renderer (pdf.js, Acrobat, Poppler) would
produce essentially identical numbers — the spec is unambiguous. We
chose MuPDF because the CLI is small, scriptable, and packaged
everywhere (Debian: `mupdf-tools`).
